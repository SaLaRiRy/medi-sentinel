# ADR-0001: 使用 Alembic 管理数据库 Schema 迁移

**状态**：已接受
**日期**：2026-10-03
**相关**：TICKET-001（工程骨架与契约 seam）

## 背景

新项目从空库开始，必须自行决定表的创建方式与后续 Schema 变更方式。`SPEC.md` 第 7.8 节把「补全建表脚本」列为范围外，因此不会沿用参考实现的建表脚本。候选方案有三种：

1. **元数据建表**：由 ORM 模型定义直接建出当前 Schema。
2. **Alembic 迁移**：每次 Schema 变更对应一个版本化的迁移脚本。
3. **建表脚本**：手写 SQL 文件并导入。

## 决策

使用 **Alembic** 管理 Schema 的创建与演进。

## 理由

- 项目要**长期演进**。元数据建表只能建出「当前模型的样子」，无法表达从上一版到这一版的变更过程。
- 建表脚本**不可追溯**：看不到某次 Schema 变更是何时、为何发生的。
- Alembic 是 SQLAlchemy 2.0 官方推荐的迁移工具，支持异步引擎，与本项目「数据访问全异步」的约束一致。
- 迁移历史本身就是一份**可审计的文档**：每次变更都留下时间、顺序与内容，评审时可与模型定义对照。

## 后果

- 首次建库通过迁移完成，不依赖建表脚本；`SPEC.md` 7.8 排除建表脚本补全依然成立。
- 每次模型变更都必须伴随一次迁移，代码评审需检查迁移与模型是否一致。
- `TICKET-001` 的验收标准由「三选一」改为「使用 Alembic」。
- 迁移历史纳入版本控制，成为 Schema 演进的可审计记录。
